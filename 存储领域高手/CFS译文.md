# CFS: Scaling Metadata Service for Distributed File System via Pruned Scope of Critical Sections

##  Abstract

分布式文件系统中，元数据可扩展性与 POSIX 语义之间存在根本性矛盾。其瓶颈在于为确保强元数据一致性（即原子性和隔离性）而采用的协调机制，主要是锁机制。CFS 是一款具备可扩展性且完全兼容 POSIX 标准的分布式文件系统，它通过缩减临界区范围以降低锁开销，从而突破元数据管理的瓶颈。首先，CFS 采用分层元数据组织方式，结合合适的分区和索引方法，使文件属性与剩余的命名空间层次结构能够独立扩展，消除跨分片的分布式协调。其次，通过单分片原子原语提升单个元数据分片的性能，缩短元数据请求的生命周期并消除虚假冲突。最后，CFS 移除元数据代理层，采用轻量级、可扩展的客户端元数据解析机制。CFS 已在百度智能云的生产环境中稳定运行三年。基于 50 节点集群的微基准测试表明，CFS 相比 HopsFS 和 InfiniFS 等基准系统，吞吐量分别提升 1.76-75.82 倍和 1.22-4.10 倍，平均延迟分别降低高达 91.71% 和 54.54%。在高竞争和大型目录场景下，CFS 的吞吐量优势进一步扩大一个数量级。针对三类包含数据访问的真实工作负载，CFS 相比 InfiniFS 实现了 1.62-2.55 倍的端到端吞吐量提升，尾部延迟降低 35.06-62.47%。

## 1 引言

自 GFS [22] 和 HDFS [24] 问世后的二十年间，分布式文件系统（Distributed File Systems, DFS）一直遵循着一种常规设计思路：将元数据管理与文件数据存储解耦，以实现二者的独立扩展；同时，系统运行在一个由多台机器组成的集群上，每台机器被分配特定角色，例如元数据服务器（Metadata Server, MDS）或存储服务器 [28, 39, 43, 55, 63, 70, 76]。在这种架构下，客户端在访问数据前，必须先与元数据服务器建立连接。

元数据性能的扩展至关重要，原因有两点。首先，在现代工作负载中，文件数量正以前所未有的规模增长，且大多数文件体积较小（例如几 KB 到几十 KB）[7, 11, 27, 57, 74, 75]，这使得元数据操作在整个文件系统操作中占主导地位。其次，得益于存储服务器间文件数据的均衡分配所支持的并行处理 [24, 35, 42]，以及快速发展的存储介质的应用 [10, 31]，数据访问速度已得到极大提升。

遗憾的是，元数据的可扩展性受到了制约，根源在于为满足绝大多数应用对 POSIX 语义 [12, 25, 30] 的需求，必须保证元数据在原子性和隔离性层面的强一致性。传统方法严重依赖事务来整合 POSIX 系统调用中的多个元数据修改操作，并通过基于锁的协调机制应对故障和避免数据竞争 [44, 48]。然而，我们的研究发现，锁开销的代价极高 —— 在无竞争的理想情况下，锁开销仍占元数据请求处理耗时的 52.91%；而在高竞争工作负载下，这一比例更是高达 93.86%。

为实现负载均衡，元数据通常会采用细粒度分区策略 [28, 42, 48, 52, 63, 76]，但这种策略会导致跨分片访问，进而加剧上述协调问题。近年来，有研究方案 [40, 44, 54, 55, 70] 尝试通过在分片时对相关元数据进行分组，以降低分布式锁和协调的开销。但这种做法需要付出代价：一方面，会牺牲文件属性服务的负载均衡性（而生产环境中文件属性的访问频率极高）；另一方面，也会丧失单个元数据分片的可扩展性。

本文提出了一种高可扩展、完全兼容 POSIX 标准的分布式文件系统 CFS，其元数据服务的扩展能力通过以下创新设计实现。

首先，我们采用分层元数据组织方式，在实现文件属性海量访问请求均衡处理的同时，缩减跨分片元数据请求的临界区范围。我们认为，文件属性与其余命名空间层次结构适用于不同的分区方式以实现扩展。因此，在 CFS 中，这两类元数据并未被同等对待，而是通过分层存储进行管理：文件属性被存储在靠近其数据的存储节点上，而剩余的命名空间层次结构则由分布式数据库层托管。这种设计不仅缓解了分布式数据库层的压力，还能通过对命名空间层次结构采用保局部分区策略，消除跨分片事务及其相关的协调开销。另一方面，文件属性通过哈希分区与文件数据实现同步均衡，从而避免热点问题。

其次，我们在数据库层设计了若干单分片原子原语。对于单个元数据请求中涉及读写多个元数据对象的多个命令，这些原语可将其整合为单个命令，在单个元数据分片中快速执行。为支持各类元数据请求，这些原语被设计为参数化函数，可通过不同输入实例化。此外，冲突协调流程能够消除并发元数据请求间的虚假冲突（此类冲突易于合并），使这些请求无需获取锁即可并行执行。这些设计共同提升了单个分片的处理能力。

最后，我们将上述两项设计原则整合到 CFS 系统中。由于元数据处理流程得到简化，CFS 进一步优化了现代元数据服务架构 —— 移除元数据代理层，将元数据解析功能整合到客户端库中。值得注意的是，CFS 已在百度智能云生产环境中部署运行三年，支持社交网络、在线购物、机器学习等各类应用场景。

我们在 50 节点集群上，通过元数据基准测试和生产工作负载对 CFS 进行了评估。实验结果表明：在无竞争场景（所有系统均处于最佳性能状态）下，在所有微基准测试中，CFS 将 HopsFS 和 InfiniFS 的峰值吞吐量分别提升高达 75.82 倍和 4.10 倍，延迟分别降低高达 91.71% 和 54.54%；在高竞争工作负载下，CFS 的扩展性能显著优于基准系统 —— 例如，其 getattr 和 mkdir 操作的吞吐量分别达到每秒 344 万次和 1.796 万次，是 InfiniFS 的 34.19 倍和 54.48 倍；在三类启用数据访问的生产工作负载中，与 InfiniFS 相比，CFS 实现了 1.62-2.55 倍的端到端吞吐量提升。



## 2 研究背景与动机

已有研究表明，元数据的可扩展性与文件数据的可扩展性同等重要，甚至更为关键 —— 在现代工作负载中，元数据操作在整个文件系统操作中占据主导地位 [1, 3, 37]。为验证这一结论，我们对百度智能云中 9 个代表性应用（涵盖社交网络、在线购物等领域）的分布式文件系统（DFS）工作负载进行了分析，统计了元数据操作与数据操作的占比。结果令人惊讶：元数据操作占分布式文件系统总请求数的比例高达 67%-96%；在倾斜最严重的工作负载中，元数据操作的占比更是数据操作的 28.2 倍。

### 2.1 分布式文件系统中的元数据管理

二十年前，GFS [22] 和 HDFS [24] 率先将元数据与文件内容解耦，元数据由单独的元数据服务器（MDS）管理，系统设计重点面向多 GB 级别的大文件。然而，当前文件规模呈现出新趋势：文件大小逐渐缩小至几十 KB，而文件数量却持续激增（例如达到数十亿个），这一趋势不仅削弱了早期设计的适用性，也推动了新设计的诞生 [39, 48, 71]。为实现元数据服务的横向扩展，CephFS [70]、Lustre [43] 等现代分布式文件系统采用了命名空间分区策略 —— 将文件系统命名空间分布到多个元数据服务器组成的集群中，以支持元数据请求的并行处理。

![image-20251028231111538](C:\Users\dell\AppData\Roaming\Typora\typora-user-images\image-20251028231111538.png)

HopsFS [48] 和 InfiniFS [44] 则采用了解耦式元数据架构，包含多个可独立扩展的元数据层。图 1 展示了此类分布式文件系统的架构，其元数据服务分为两层：一组数据库实例将元数据组织为数据库记录和表，这些记录与表进一步分片并分布式存储以实现负载均衡；此外，代理层在数据库层之上构建文件系统元数据逻辑（例如将元数据操作封装为数据库事务）。这种解耦式设计已被应用于 Azure ADLS [54]、Facebook Tectonic [52] 等工业级系统中。

### 2.2 强元数据一致性带来的高额开销

为支持丰富的应用场景，绝大多数分布式文件系统 [12, 25, 32, 40, 43, 46] 均提供 POSIX（或类 POSIX）语义 [6, 23, 30, 68]，而该语义要求元数据在原子性和隔离性层面保持强一致性。其中，原子性可确保在发生故障时避免部分更新导致的不一致状态，隔离性则能协调并发元数据请求，防止有害数据竞争留下的异常状态。

![image-20251028231516369](C:\Users\dell\AppData\Roaming\Typora\typora-user-images\image-20251028231516369.png)

元数据的 POSIX 语义通常通过事务机制保障：每个事务会将若干元数据读写操作组合在一起，并以原子、隔离的方式执行这组命令。图 2 展示了 HopsFS 中文件创建（create）元数据请求的事务构成：首先通过一条读取语句（第 2 行）获取目标父目录的元数据，随后通过条件判断（第 3 行）验证父目录是否存在；若存在，则执行两条写语句 —— 先为新文件创建元数据记录（第 4 行），再更新命名空间层次结构，将新创建的文件元数据与父目录关联（第 5 行）；最后，事务提交以持久化所有变更（第 6 行）。

![image-20251028231459426](C:\Users\dell\AppData\Roaming\Typora\typora-user-images\image-20251028231459426.png)

现代分布式文件系统的元数据服务 [32, 44, 48, 55, 64] 高度依赖代价高昂的锁机制来实现原子性和隔离性，确保正在执行的元数据事务不会读取其他事务的部分结果，且冲突事务能够按序执行。图 3 展示了上述事务的执行流程：文件系统客户端通过向元数据代理发送创建请求（①）启动事务，该代理负责在 HopsFS 元数据服务内部协调事务执行；代理从某个分片读取父目录元数据，并同时获取父目录的写锁（②）；读取和加锁成功后，代理与对应的元数据分片（根据分区方式不同，可能与父目录分片相同）通信，执行文件元数据创建和父目录元数据修改操作（③-④）；最后，事务提交且锁释放（⑤）后，客户端会收到通知（⑥）。需注意，步骤⑤可能需要通过两阶段提交协议（2PC）协调跨分片变更的原子执行。

为探究锁开销及其对元数据可扩展性的负面影响，我们部署了一个小规模 HopsFS 集群，其元数据服务包含 3 个数据库实例（详见 5.1 节），并通过 3-48 个并发客户端发起创建操作，同时通过客户端访问同一目录的概率来模拟不同的竞争率。图 4（a）显示，在无竞争场景下，HopsFS 元数据服务的吞吐量随客户端数量增加几乎呈线性增长；但随着竞争率提升，元数据性能显著下降，当竞争率达到 100% 时，吞吐量曲线趋于平缓。

![image-20251028231426979](C:\Users\dell\AppData\Roaming\Typora\typora-user-images\image-20251028231426979.png)

我们在图 4（b）中进一步拆解了文件创建操作的延迟构成。首先，即便在无竞争场景下，HopsFS 仍需承担巨大的锁开销 —— 占整个元数据请求处理耗时的 52.91%。其次，“执行” 步骤（包含③-⑤）和除步骤②外的其他内部处理（“Others”）耗时在不同竞争率下几乎保持稳定；与之相反，锁开销则大幅增加：当竞争率为 50% 和 100% 时，锁开销占元数据请求平均耗时的比例分别达到 83.18% 和 93.86%。需注意，元数据访问的高竞争场景并不罕见，多项研究及我们的实践经验表明，大数据分析等应用常会并发读写共享目录 [48, 52]。

遗憾的是，元数据分区策略（提升元数据负载均衡性和整体性能的关键手段）会进一步加剧锁机制的复杂性。一方面，许多系统采用哈希等细粒度分区方式，以实现元数据访问在各分片间的完美均衡 [28, 43, 63, 76]，但这种方式会引入跨分片元数据事务，直接导致临界区范围扩大和锁开销增加。另一方面，部分系统采用保局部分区策略（如 CephFS [70] 的子树分区、[8, 20, 54] 的范围分区、InfiniFS [44] 的父子分组）以消除跨分片事务，但这会带来潜在的热点问题 [47, 59, 69]。在最坏情况下，锁机制会导致单个分片上的所有事务串行执行，同样限制元数据服务的整体性能。





## 3 CFS 系统概述

### 3.1 设计原理

本文旨在构建 CFS—— 一款高可扩展、完全兼容 POSIX 标准的分布式文件系统，其元数据服务可通过横向扩展实现高吞吐量与低延迟。为此，我们借鉴了前文提及的元数据解耦与解聚架构，但通过一系列创新方法，在保障强元数据一致性的前提下，安全缩减元数据请求的临界区范围以降低协调开销。我们的设计基于以下关键观察与创新，与以往的设计假设存在显著差异。

首先，我们致力于将元数据请求的执行范围从跨分片缩减至单分片，以消除分布式协调。这需要重新思考元数据对象的组织方式，从而同时应对其不同的访问模式与扩展特性。如表 1 所示，getattr¹ 等绝大多数元数据操作主要针对文件属性，这类操作更适合扁平式组织，且常与数据操作并行访问；与之相反，create（创建文件）、unlink（删除文件）等与目录相关的元数据操作，需要先插入或删除文件索引节点（inode），再修改其父目录的索引节点属性，因此更适合保留命名空间的层次结构，并将父目录属性与子目录 / 文件的索引节点集中存储。

> ¹getattr 并非 POSIX 标准接口，但却是 NFS 等分布式文件系统中实现 open、stat 等 POSIX 接口的常用元数据操作。

这一趋势促使我们将元数据管理拆分为两个独立层级：命名空间层次结构仍由分布式数据库层通过保局部分区策略和丰富语义进行管理；而文件属性则由另一存储层级通过哈希分区和简单的键值接口进行管理。

其次，我们通过安全放宽事务的原子性与隔离性（例如可串行化快照隔离 [9]），进一步缩减元数据请求的临界区 —— 这些被放宽的特性对于保障 POSIX 元数据语义而言过于严格。我们认为，元数据事务并非任意形式，而是具有极强的规律性。通过对 POSIX 接口的分析，我们得出结论：在无协调机制的情况下，仅可能出现两类不一致问题：（1）映射损坏，例如文件创建成功但未能与父目录建立关联；（2）更新丢失，例如两个并发请求在同一父目录下创建子目录时，均覆盖父目录的链接数（links）属性，导致最终链接数比实际值少 1。

借助分层元数据组织，我们可通过在两个层级间按确定顺序执行元数据变更，容忍映射损坏问题 —— 即便文件系统索引在内部出现损坏，外部也始终无法感知（即损坏状态对外部不可见）。此外，我们可将单分片元数据事务中涉及多个对象的逻辑整合为一个原子操作，一次性执行，从而缩减其临界区范围，大幅降低事务的生命周期与锁开销。同时，针对更新丢失问题，我们利用并发更新可合并的特性，将这类冲突视为 “虚假冲突”，安全地将其排除在临界区之外。

第三，与当前主流方案相比，我们的元数据代理层已大幅简化 —— 不再负责协调事务与跟踪锁状态，仅剩的功能是解析客户端的元数据请求，并将其路由至元数据服务中的相应组件。基于此，我们认为无需再维护独立的元数据代理层，而是可将其功能整合到客户端库中，实现轻量级的客户端侧元数据解析。这种设计不仅简化了元数据服务架构，避免了额外的通信步骤，还能自然支持大量客户端的横向扩展。

#### 命名空间存储层（TafDB）

我们部署 TafDB 作为命名空间存储层，通过一组定制化原语和安全放宽的原子性、隔离性（详见 4.1 节与 4.2 节），在分布式数据库中管理除文件属性外的命名空间层次结构。TafDB 进一步分为两个子模块：其一为时间服务器组（Time Servers, TS），负责分配单调递增的时间戳，用于对元数据事务进行排序；其二为后端服务器组（Backend Servers, BE），以数据库表的形式存储元数据信息。为保障高可用性，BE 的状态通过 Raft 共识协议 [49] 进行分组复制与协调管理。所有通过 TafDB 执行的元数据变更，均需先持久化到目标 Raft-BE 组内复制的预写日志（Write-Ahead Log, WAL）中。

#### 文件存储层（FileStore）

FileStore 是一款扁平的分布式对象存储，用于存储 CFS 中的数据块（文件数据的存储单位）。每个 FileStore 节点还运行一个本地 RocksDB [61] 实例，用于存储对应文件的属性元数据，以实现元数据的快速检索。为保障高可用性，每个数据块与元数据预写日志（WAL）均在多个 FileStore 实例间进行复制，通常采用三副本策略。

#### 重命名服务（Renamer）

我们专门设计了 Renamer 服务，用于处理复杂的重命名（rename）元数据请求 —— 这类请求可能引发异常，无法由 TafDB 独立处理（与 InfiniFS [44] 类似）。若通过增强 TafDB 来支持此类请求，需启用最强隔离级别，这会给其他类型的元数据请求带来不必要的性能损耗。Renamer 由一组受 Raft 保护的服务器构成，其中一个被指定为协调器。协调器会检查复杂重命名请求的合法性，并通过读写 TafDB 与 FileStore 执行合法请求。这种设计允许以较小规模部署 Renamer 集群，降低部署成本，具体细节将在 4.3 节展开。

#### 客户端库（ClientLib）

ClientLib 是 CFS 的入口，向应用程序提供 getattr、create、mkdir 等元数据操作，以及 open、read、write 等文件操作接口。由于 ClientLib 缓存了 TafDB 与 FileStore 的分区信息，可实现客户端侧元数据解析，并直接与 CFS 的各组件交互，从而缩短请求处理时长。整体而言，ClientLib 与 CFS 其他组件间存在三条交互路径：文件数据与属性请求发送至 FileStore，复杂重命名请求转发至 Renamer，其余请求提交至 TafDB。

#### POSIX 文件系统接口兼容性

CFS 通过 VFS（虚拟文件系统）适配器实现 POSIX 语义兼容 —— 该适配器位于 Linux 内核中，作为 “转换器” 将 POSIX 文件系统接口映射为各文件系统具体实现提供的底层函数。具体而言，CFS 将 ClientLib 挂载到 VFS，并实现 VFS 的相关函数，将用户态 POSIX 函数调用编排为 CFS 内部的元数据或数据操作。例如，带有 O_CREAT 标志的 POSIX open 接口，若目标文件不存在，会在 CFS 内部触发 lookup（查找）与 create（创建）两类元数据操作；又如，用于读取文件内容的 POSIX read 接口，会在 CFS 中触发以下流程：ClientLib 向 FileStore 发起 getattr 请求，获取文件修改时间等属性；若修改时间与缓存中的不一致，则进一步向 FileStore 发起 read 请求以获取目标数据。为提升易用性，CFS 还额外提供了与 FUSE [21]、Samba [66] 和 NFS-Ganesha [19] 兼容的接口。

为验证 CFS 对 POSIX 文件系统接口的完整兼容性，我们使用常用测试套件 pjdfstest [53] 对其进行了全面测试，并与 ext4、XFS、CephFS 等主流文件系统实现进行对比。测试日志可参见 [13]，结果显示：ext4 与 CFS 均通过了全部 8832 个测试用例，而 XFS 和 CephFS 分别失败 2 个和 237 个测试用例。

## 4 设计与实现

### 4.1 元数据组织与分区

#### 在 TafDB 中存储命名空间层次结构以提升局部性

![image-20251028232734120](C:\Users\dell\AppData\Roaming\Typora\typora-user-images\image-20251028232734120.png)

如图 6（右上部分）所示，我们将除文件属性外的文件系统元数据组织到 TafDB 的一张全局`inode_table`表中。不同于传统设计 [48, 54] 将元数据分散存储在多张表中，这种统一设计简洁且高效 —— 可避免在处理 create（创建文件）等需同时更新父目录元数据的操作时，维护跨表一致性的复杂逻辑。与 InfiniFS [44] 类似，我们将每个目录索引节点（inode）拆分为两条数据库记录：一条是索引节点 ID 记录（第 1 行），另一条是属性记录（第 2 行）。这种拆分可避免访问这两类记录时产生的竞争冲突。此外，该表还存储文件索引节点 ID 记录（第 3-4 行）。

所有表记录共享统一的复合主键`<kID, kStr>`，其中`kID`表示索引节点 ID，`kStr`为字符串字段。对于每条目录或文件的 ID 记录，`kID`和`kStr`分别对应其父目录的索引节点 ID 与自身的目录名 / 文件名（如图 6 中的第 1、3、4 行）；而对于每条目录属性记录，`kID`设为该目录自身的索引节点 ID，`kStr`则设为保留关键字 “/_ATTR”（如图 6 中的第 2 行）。此外，每条记录包含若干可选字段（如 id、type、children、links、size、time 等)，未使用的字段设为 NULL。

我们基于`kID`值采用范围分区策略，将`inode_table`划分为多个分片（TafDB 中的元数据存储单位），并将这些分片分布到后端服务器上。上述元数据组织方式与基于`kID`的范围分区相结合，可实现局部性保留 —— 将一个目录的属性及其所有子目录 / 文件的索引节点 ID 存储在同一个元数据分片上。即便对于包含数百万个文件的大型目录（这类目录并不少见 [48]），该设计依然适用：由于我们将文件属性卸载到 FileStore 中（下文详述），而每个文件属性仅占用 0.2KB 存储空间，因此超大型目录的元数据也不会超出单个 TafDB 分片的存储容量。

最后，我们引入了若干定制化原语（详见 4.2 节），以简化与目录相关的元数据读写操作 —— 这些原语比 SQL 查询更简洁，同时比键值接口具备更强的语义。

#### 在 FileStore 中存储文件属性以优化负载均衡与消除热点

我们将文件属性存储在与其数据所在的同一 FileStore 节点上。每个 FileStore 节点运行一个本地 RocksDB 实例（如图 6 右下部分所示），该实例将文件属性组织为键值对：键为文件索引节点 ID，值为文件属性编码后的字节流（与上述目录属性的编码方式类似）。由于键值接口简洁，通过 FileStore 操作文件属性的开销低于通过 TafDB 操作的开销。

此处未采用范围分区，而是通过计算文件索引节点 ID 的哈希值，将文件属性与其数据一同均匀分布到 FileStore 的各个存储节点上。这种设计支持从多个存储节点并行处理文件属性请求，即便在大型目录场景下也能实现负载均衡。在传统方案中，保局部分区策略会将同一目录下所有文件的属性存储在单个元数据分片上，极易引发热点问题；而 CFS 通过为命名空间层次结构与文件属性分别设计适配其访问模式的分区策略，突破了这一限制。

#### 分布式事务消除

元数据跨 TafDB 与 FileStore 存储时，为保障原子性，理论上需协调涉及这两个组件的分布式事务。为消除此类协调开销，我们精心设计了元数据请求的执行流程 —— 通过固定的执行顺序执行变更操作，确保执行过程中发生故障时不会导致有害的不一致状态。核心思路是：对于创建类元数据请求，将文件系统命名空间层次结构的更新作为最后一步；对于删除类元数据请求，则将该更新提前作为第一步。这种设计以在 FileStore 中引入 “孤儿” 属性记录（对外不可见）为代价，避免了更重要的文件系统索引损坏。不过，这类良性不一致可通过后台定期执行的垃圾回收机制清理（详见 4.4 节）。图 7 列出了 create（创建文件）、unlink（删除文件）、file rename（文件重命名）三类典型元数据请求的执行顺序。以 create 为例：若在 FileStore 中完成属性插入后发生崩溃，恢复时 TafDB 中的索引保持不变，后续任何访问都无法感知到这条新插入的属性记录。

![image-20251028232902215](C:\Users\dell\AppData\Roaming\Typora\typora-user-images\image-20251028232902215.png)

此外，由于文件属性卸载、`inode_table`统一索引设计与范围分区策略的结合，CFS 可将目录属性与子目录 / 文件的 ID 记录集中存储在 TafDB 的同一个分片上。因此，传统设计中普遍存在的分布式事务，在 CFS 中绝大多数可转化为单分片事务。

### 4.2 TafDB 中的高效单分片原语

接下来，我们通过以下技术缩减元数据请求的临界区范围，提升单个 TafDB 分片的性能。

#### 单分片原子原语

如图 2 所示，多数元数据事务需访问多条记录，并遵循 “读取 - 修改” 模式。若直接基于 TafDB 的`inode_table`实现这类事务，需将逻辑拆分为多条读写语句，并包含必要的一致性检查，且需 ClientLib 以交互方式逐句执行，效率极低。为此，我们提出通过三类单分片原子原语，将单个元数据请求涉及的所有变更操作一次性执行 —— 这些原语是支持读写与条件检查的参数化函数，具体如表 2 所示。

**表 2 TafDB 提供的单分片原子原语（表中 “cond” 表示条件）**

| 原语（Primitives）              | 适用场景（Use cases）                                        | 语法（Syntax）                                               | 描述（Description）                                          |
| ------------------------------- | ------------------------------------------------------------ | ------------------------------------------------------------ | ------------------------------------------------------------ |
| `insert_with_update`            | create（创建文件）、mkdir（创建目录）、symlink（创建符号链接）、link（创建硬链接） | `INSERT (value_list) WITH UPDATE table_name SET (assignment_list) WHERE (update_cond)` | （1）检查是否存在匹配`update_cond`的记录；（2）插入一条新的索引节点 ID 记录；（3）根据`assignment_list`更新已存在的记录。 |
| `delete_with_update`            | unlink（删除文件）、rmdir（删除目录）                        | `DELETE (delete_cond) WITH UPDATE table_name SET (assignment_list) WHERE (update_cond)` | （1）检查是否存在匹配`delete_cond`/`update_cond`的记录；（2）删除匹配`delete_cond`的记录；（3）根据`assignment_list`更新匹配`update_cond`的记录。 |
| `insert_and_delete_with_update` | rename（重命名）                                             | `INSERT (value_list) WITH DELETE (delete_cond_list) WITH UPDATE table_name SET (assignment_list) WHERE (update_cond)` | （1）检查是否存在匹配各自指定条件的记录；（2）删除匹配`delete_cond_list`中任一条件的记录；（3）插入一条新的索引节点 ID 记录（主键与字段按`value_list`指定的内容更新）；（4）根据`update_cond`与`assignment_list`更新记录。 |

仅当条件检查结果为 “真” 时，TafDB 才会执行所有变更操作；否则不执行任何操作。TafDB 支持通过类 SQL 语法灵活定义检查条件：首先，允许在原语的`WHERE`子句中指定谓词 —— 例如，对于 “存在性检查” 与 “目录空性检查” 这两类关键检查，只需在`WHERE`子句中明确指定主键或 “children = 0” 即可；其次，支持将谓词与`DELETE`/`UPDATE`子句关联，若对应状态变更失败，则可判断特定条件未满足；最后，`INSERT`操作默认支持隐式存在性检查 —— 若因记录重复导致插入失败，即表示存在性检查通过。更多示例可参见图 8。

这些原语的优势如下：首先，大幅减少 ClientLib 与 TafDB 之间的通信交互；其次，通过 TafDB 单命令快速执行，缩短元数据事务的生命周期与锁竞争时间；第三，简化元数据请求设计 —— 这些原语可通过不同参数实例化，在各类请求中复用，无需为每个请求单独实现逻辑。需注意，该设计看似与数据库存储过程 [33] 类似，但存在本质区别：存储过程仅简单地将多条语句分组，执行时仍需逐条处理；而我们的原语本身就是单条语句，执行效率更高。

#### 冲突协调流程

然而，上述原语仍存在锁开销，TafDB 为保障语义正确性，可能会将原语串行执行。为进一步降低锁开销，我们发现一个重要特性：当多个元数据请求并发读写同一父目录的属性时，会产生 “虚假竞争”。以 create 操作为例：两个并发请求在同一目录下创建文件时，均需更新`inode_table`中该目录记录的`links`、`children`、`size`、`mtime`字段，但我们认为这类属性冲突更新完全可合并。具体而言，元数据属性的变更仅存在两类情况：第一类是`links`、`children`、`size`等数值型属性，其变更仅为增减操作且副作用具有交换性 —— 即便不通过锁保护，以任意顺序应用这些增量变更，最终仍能得到一致的结果；第二类是`time`、`permission`等非数值型属性，其最终值由 “最后修改者” 决定，而 “最后修改” 可通过全局统一的顺序确定。

基于此，我们通过为单分片原子原语增加两类冲突协调流程，将虚假竞争排除在临界区之外：首先，针对数值型属性的增减操作，引入 “增量合并流程”—— 在原语中编码正负增量值，允许数据库以任意顺序将这些值应用到记录中；其次，针对非数值型属性的覆盖更新，“增量合并流程” 不再适用，转而采用 “最后写入获胜” 策略 [36]—— 依赖 TafDB 分配的单调递增时间戳，将时间戳最大的更新结果作为最终值。

#### 案例分析

此处以文件创建与删除两类元数据操作的实现为例，展示上述原语的应用。如图 8（a）所示，create 操作首先执行 FileStore 元数据操作（第 2 行），将文件属性键值对插入 RocksDB，随后向 TafDB 发起`insert_with_update`原语调用（第 4-7 行）。该原语确保：若对应的父目录存在，则在`inode_table`中插入新文件的索引节点 ID 记录，并相应更新父目录的属性。其中，“children += 1”（第 6 行）与 “mtime = now”（第 6 行）分别展示了 “增量合并” 与 “最后写入获胜” 流程的应用。同样，这两步插入操作无需任何锁保护。类似地，图 8（b）展示了文件删除操作的代码片段：TafDB 通过`delete_with_update`原语（第 2-5 行），原子性地完成两项操作 —— 从`inode_table`中删除文件的索引节点 ID 记录、将对应父目录的`children`字段减 1，随后通过 FileStore 执行属性删除操作（第 6 行）。

### 4.3 强一致性重命名

重命名（rename）是最复杂的元数据操作，需保障最强一致性 —— 在最坏情况下，单个重命名请求可能涉及 6 个元数据对象的变更（目标文件或对应父目录的 4 条属性记录与 2 条索引节点 ID 记录），且这些对象可能分布在不同元数据分片上。尽管重命名操作的占比相对较低（如表 1 所示），但优化其性能仍具有重要意义 —— 这类操作会对请求尾部延迟与元数据服务可扩展性产生负面影响。我们的优化方案基于另一关键观察：在生产工作负载中，绝大多数（近 99%）重命名请求针对同一目录下的两个文件。目录内文件重命名操作因变更局限在单个分片内，实现相对简单；而其他类型的重命名操作则需通过协调保障语义正确性，因此 CFS 对这两类场景采用差异化处理。

#### 快速路径（Fast Path）

对于同一目录下的文件重命名，我们通过优化执行路径避免调用 Renamer——ClientLib 直接与 TafDB、FileStore 交互，并利用 TafDB 的`insert_and_delete_with_update`原语完成操作。该设计可行的原因在于：POSIX 重命名请求会触发 CFS 内部的 lookup（查找）与 getattr（获取属性）元数据操作，ClientLib 会缓存获取到的目标索引节点信息，足以判断重命名操作是否符合 “快速路径” 条件。

图 8（c）展示了这类重命名请求的代码片段（假设源文件为 A、目标文件为 B）。在 TafDB 中，需满足以下条件：（1）源文件 A 必须存在 —— 由`DELETE`子句中第一组括号内的谓词（第 3 行）联合判断；（2）目标文件 B 不存在，或 B 存在且为文件 —— 由第二组括号内的谓词联合 “ifexist” 关键字（忽略 B 不存在时的删除失败）指定。条件检查通过后，将执行以下元数据变更：首先，插入一条新的文件 ID 记录，其复合主键为`<parent_id, "B">`，`id`字段设为 A 的索引节点 ID（第 2 行）；其次，删除源文件 A 与目标文件 B 的旧索引节点 ID 记录（第 3 行）；最后，更新父目录的属性（第 4-6 行）。需注意，`children`字段的增量由 TafDB 内部计算 —— 若 A、B 中任一文件不存在，增量为 0；若两者均存在，增量为 - 1。TafDB 内的变更完成后，若 B 的属性记录存在，则从 FileStore 中删除该记录（第 7 行）。与 4.1 节所述一致，这两个阶段的执行无需协调。

#### 普通路径（Normal Path）

除快速路径外的其他重命名请求更为复杂，需特殊处理，原因有二：首先，这类请求可能涉及不同父目录下的文件 / 目录，而这些父目录的元数据可能分布在不同 TafDB 分片上 —— 此时无法使用单分片原语，需由专门的 Renamer 协调器采用传统的锁机制与两阶段提交协议，在 FileStore 与 TafDB 之间执行一系列元数据变更，以保障并发重命名操作的一致性；其次，普通路径重命名可能引发 POSIX 语义不允许的 “孤儿循环”—— 两个目录互为父目录，且其元数据子树与其余元数据层次结构断开连接。这种情况可能发生在将祖先目录重命名为其后代目录时，或因未协调的并发普通路径重命名请求导致。为避免该问题，Renamer 会先获取源 / 目标目录 / 文件及其最近公共祖先目录的锁，再验证请求是否存在 “孤儿循环” 风险 [30]。

最后，快速路径与普通路径的重命名操作不会相互干扰，原因如下：第一，快速路径重命名仅涉及文件（不涉及目录），天然不存在 “孤儿循环” 风险；第二，CFS 为快速路径重命名使用的单分片原子原语与普通路径使用的传统分布式事务提供强隔离性，可避免不一致问题。

### 4.4 垃圾回收

由于 FileStore 与 TafDB 均通过 Raft 容错协议保护，数据不一致仅可能在以下场景发生：ClientLib 在执行跨 TafDB 与 FileStore 的元数据请求过程中崩溃，或与 CFS 元数据服务发生网络分区。为此，CFS 通过轻量级垃圾回收器清理这两个组件中的 “孤儿” 记录（即无关联索引的孤立数据）。具体而言，垃圾回收器通过监听 TafDB 与 FileStore 的预写日志（WAL），获取近期元数据变更（类似广泛使用的变更数据捕获服务 [17]），并对两者间的相关元数据变更进行配对分析，识别不匹配的 “孤儿” 记录。

垃圾回收器在后台运行，与前台请求隔离，支持两种工作模式：第一种是定期模式 —— 回收器按固定时间间隔启动分析，若 FileStore 增量 WAL 中出现新属性记录，但 TafDB 对应 WAL 中无匹配的索引节点 ID 记录，则判定为 “崩溃的创建操作”；对于 unlink（删除文件）与 file rename（文件重命名）操作，由于 TafDB 中的元数据删除先于 FileStore 执行，回收器会识别 TafDB 中已删除索引节点 ID 对应的 FileStore 残留属性记录。第二种是按需模式 —— 针对 rmdir（删除目录）操作可能出现的损坏场景，当 getattr（获取属性）与 readdir（读取目录）操作无法获取属性记录时，触发回收器回收 “孤儿” 索引节点 ID。



## 6 相关工作

### 6.1 元数据解耦与解聚

为实现命名空间与数据的独立扩展，现代分布式文件系统已普遍将元数据与数据解耦 [22, 42, 46]。为适配现代工作负载中 “海量小文件” 与 “高并发元数据访问” 的特点，研究者提出了解耦式元数据架构，将元数据服务与元数据存储进一步解耦。近年来，CalvinFS [64]、HopsFS [48]、ADLS [54]、Tectonic [52]、InfiniFS [44] 等分布式文件系统均采用 CalvinDB [65]、NDB [77]、ZippyDB [5] 等高性能数据库实现元数据存储的横向 / 纵向扩展，同时通过独立的元数据代理层作为网关与客户端交互。本文在继承这一解耦架构的基础上进行创新：移除元数据代理层，采用客户端侧元数据解析机制。

### 6.2 元数据组织与分区

HopsFS [48] 将元数据组织为 MySQL 数据库表，而 Tectonic [52] 与 InfiniFS [44] 则将元数据映射为键值对；此外，Tectonic 将文件系统元数据拆分为命名层、文件层与块层，InfiniFS [44] 则将目录元数据分为访问信息与内容信息两类。这些系统均在同一存储内部，通过不同索引与映射方式管理逻辑分离的命名空间层次。本文进一步挖掘文件属性与其余命名空间层次结构的差异，采用 TafDB 与 FileStore 构成的分层存储架构对二者进行分别管理。

为实现元数据访问并行化，BeeGFS [28]、LustreDNE2 [43]、SoMeta [63]、SkyFS [72]、PVFSv2 [29]、HBA [76]、CalvinFS [64]、Tectonic [52] 等系统采用哈希分区策略，但需以引入跨分片协调为代价。与之相反，Sprite [50]、Coda [58]、Ursa Minor [2]、Lustre-DNE1 [43]、CephFS [70] 等系统采用子树分区策略以保留局部性，ADLS [54] 采用范围分区，InfiniFS [44] 则通过局部性感知分组将相关数据放置在同一分片 —— 但这些保局部分区策略易引发热点问题。本文提出的 CFS 则通过分层元数据存储，在保留命名空间局部性的同时，实现了元数据负载均衡。

### 6.3 事务与一致性

近期研究表明，POSIX 语义的实现易出现错误 [45]。为此，HopsFS [48] 将元数据操作封装为（分布式）事务，通过数据库行级锁保障隔离性，并利用两阶段提交协议确保跨分片事务的原子性；GlobalFS [51] 通过原子多播对元数据更新进行排序；Tectonic [52] 与 InfiniFS [44] 则高度依赖本地键值存储的单分片强一致性事务，要么以牺牲一致性为代价放弃分布式事务，要么依赖标准两阶段提交协议处理跨分片操作。Spanner [16]、CockroachDB [62] 等数据库通过乐观并发控制提供严格可串行化隔离，在低竞争工作负载下性能表现良好。与之不同，CFS 将元数据操作简化为单分片原子原语，摒弃（分布式）事务的设计理念，在安全放宽原子性与隔离性要求的同时，不牺牲预期语义 —— 因此，即便在高竞争工作负载下，CFS 仍能实现比上述相关工作更优的元数据可扩展性。

已有研究提出通过更弱的一致性模型，对 “保持不变性” 与 “可交换” 的操作安全放宽一致性（隔离级别）[14, 38]；此外，冲突协调是高竞争工作负载下提升吞吐量的关键思路 [18]，ElmerFS [67] 则探讨了在地理分布式文件系统中使用无冲突复制数据类型（CRDT [60]）组织元数据的方案。本文从这类研究中汲取灵感，将冲突协调与单分片原子原语结合，应用于分布式文件系统的元数据管理。其他相关工作则通过硬件优化手段提升元数据性能，例如使用单边 RDMA [41]、将元数据存储在持久内存 [4, 73]、将功能卸载到智能网卡（SmartNIC [34]）等 ——CFS 的研究重点与这类硬件驱动的解决方案互为补充、互不冲突。
