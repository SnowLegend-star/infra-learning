# Efficient Memory Management for Large Language Model Serving with PagedAttention

# Abstract 

大型语言模型（LLM）的高吞吐量服务需要一次批量处理足够多的请求。然而，现有系统面临挑战：每个请求的键值缓存（KV cache）占用内存巨大，且会动态增长和收缩。若内存管理效率低下，碎片化和冗余复制会导致内存严重浪费，进而限制批量处理规模。

为解决该问题，我们提出 PagedAttention—— 一种受操作系统中经典虚拟内存和分页技术启发的注意力算法。基于该算法，我们构建了 vLLM 这一 LLM 服务系统，它实现了：（1）KV cache 内存浪费接近零；（2）支持请求内部及跨请求的 KV cache 灵活共享，以进一步降低内存占用。

评估结果表明，与 FasterTransformer、Orca 等当前最先进的系统相比，vLLM 在保持相同延迟水平的情况下，将主流 LLM 的吞吐量提升了 2-4 倍。在长序列、大型模型和复杂解码算法场景下，性能提升更为显著。vLLM 的源代码已公开，地址为https://github.com/vllm-project/vllm。

# 1 引言

GPT [5, 37] 和 PaLM [9] 等大型语言模型（LLM）的出现，催生了编程助手 [6, 18] 和通用聊天机器人 [19, 35] 等新应用，这些应用正开始对我们的工作和日常生活产生深远影响。许多云厂商 [34, 44] 正竞相将这些应用作为云端托管服务提供给用户。然而，运行这些应用成本极高，需要大量 GPU 等硬件加速器。据近期估算，处理一个 LLM 请求的成本可能是传统关键词查询 [43] 的 10 倍。鉴于这些高昂的成本，提高 LLM 服务系统的吞吐量（进而降低单个请求的成本）变得愈发重要。

LLM 的核心是自回归 Transformer 模型 [53]。该模型基于输入（提示词）和此前生成的输出 token 序列，逐一生成单词（token）。对于每个请求，这一高成本过程会重复执行，直到模型输出终止 token。这种串行生成过程导致工作负载受内存限制，GPU 的计算能力未能得到充分利用，进而限制了服务吞吐量。

通过批量处理多个请求可以提高吞吐量。但要批量处理大量请求，必须高效管理每个请求占用的内存空间。例如，图 1（左）展示了在配备 40GB 内存的 NVIDIA A100 GPU 上运行 130 亿参数 LLM 时的内存分布。约 65% 的内存用于存储模型权重，这些权重在服务过程中保持静态；近 30% 的内存用于存储请求的动态状态 —— 对于 Transformer 而言，这些状态由与注意力机制相关的键（key）和值（value）张量组成，通常被称为 KV 缓存 [41]，它们存储了早期 token 的上下文信息，用于逐一生成新的输出 token；剩余的少量内存用于存储其他数据，包括激活值（activations）—— 即评估 LLM 时生成的临时张量。由于模型权重是固定的，且激活值仅占用 GPU 内存的一小部分，因此 KV 缓存的管理方式对决定最大批量大小至关重要。如图 1（右）所示，若管理效率低下，KV 缓存内存会严重限制批量大小，进而影响 LLM 的吞吐量。

本文中，我们发现现有 LLM 服务系统 [31, 60] 未能高效管理 KV 缓存内存。这主要是因为大多数深度学习框架 [33, 39] 要求张量存储在连续内存空间中，因此这些系统也将单个请求的 KV 缓存存储为连续内存块。但与传统深度学习工作负载中的张量不同，KV 缓存具有独特特性：随着模型生成新 token，它会动态增长和收缩，且其生命周期和长度无法提前预知。这些特性导致现有系统的方案在两方面存在显著低效问题：

首先，现有系统 [31, 60] 存在内部和外部内存碎片问题。为将请求的 KV 缓存存储在连续空间中，它们会根据请求的最大长度（例如 2048 个 token）预分配一块连续内存。由于请求的实际长度可能远短于最大长度（例如图 11 所示），这会导致严重的内部碎片。此外，即使实际长度可提前预知，预分配方式仍存在低效问题：在请求的整个生命周期内，整块内存都会被预留，其他较短的请求无法利用该内存块中当前未使用的部分。同时，由于每个请求的预分配内存大小可能不同，外部内存碎片问题也会十分突出。事实上，我们在图 2 中的性能分析结果显示，现有系统中仅有 20.4%-38.2% 的 KV 缓存内存用于存储实际的 token 状态。

其次，现有系统无法利用内存共享的潜力。LLM 服务通常会采用并行采样、束搜索等高级解码算法，这些算法会为单个请求生成多个输出。在这些场景下，一个请求包含多个序列，这些序列可以部分共享 KV 缓存。但现有系统中，各序列的 KV 缓存存储在独立的连续空间中，因此无法实现内存共享。

为解决上述局限性，我们提出 PagedAttention—— 一种受操作系统（OS）内存碎片与共享解决方案（虚拟内存分页技术）启发的注意力算法。PagedAttention 将每个请求的 KV 缓存划分为多个块（block），每个块可存储固定数量 token 的注意力键值向量。在 PagedAttention 中，KV 缓存的各个块无需存储在连续物理空间中。因此，我们可以像操作系统虚拟内存那样灵活管理 KV 缓存：可将块类比为页（page）、token 类比为字节（byte）、请求类比为进程（process）。该设计通过使用相对较小的块并按需分配，减轻了内部碎片问题；此外，由于所有块大小相同，外部碎片问题也得以消除；最后，它支持以块为粒度的内存共享，既可以在同一请求的不同序列之间共享，也可以在不同请求之间共享。

基于 PagedAttention，我们构建了 vLLM—— 一款高吞吐量分布式 LLM 服务引擎，它实现了 KV 缓存内存的近零浪费。vLLM 采用与 PagedAttention 协同设计的块级内存管理和抢占式请求调度机制，支持 GPT [5]、OPT [62]、LLaMA [52] 等多种主流 LLM，涵盖不同参数规模，包括那些超出单 GPU 内存容量的大型模型。我们在多种模型和工作负载上的评估结果表明，与 FasterTransformer [31]、Orca [60] 等当前最先进的系统相比，vLLM 在完全不影响模型精度的前提下，将 LLM 服务吞吐量提升了 2-4 倍，且在长序列、大型模型和复杂解码算法场景下，性能提升更为显著（§4.3）。

综上，我们的贡献如下：・明确了 LLM 服务中内存分配面临的挑战，并量化了这些挑战对服务性能的影响。・提出 PagedAttention 算法，该算法基于操作系统虚拟内存分页技术，可处理存储在非连续分页内存中的 KV 缓存。・设计并实现了基于 PagedAttention 的分布式 LLM 服务引擎 vLLM。・在多种场景下对 vLLM 进行评估，证实其性能显著优于 FasterTransformer [31]、Orca [60] 等此前的最先进方案。

## 2.2 LLM 服务与自回归生成

LLM 训练完成后，通常会部署为条件生成服务（例如补全 API [34] 或聊天机器人 [19, 35]）。向 LLM 服务发起的请求会提供一组输入提示词 token (*x*1,...,*x**n*)，LLM 服务将根据公式 1 生成一组输出 token (*x**n*+1,...,*x**n*+*T*)。我们将提示词与输出 token 的拼接结果称为 “序列”（sequence）。

由于公式 1 的分解特性，LLM 只能逐个采样并生成新 token，且每个新 token 的生成过程依赖该序列中所有之前的 token，尤其是这些 token 对应的键向量和值向量。在这种串行生成过程中，已生成 token 的键向量和值向量会被缓存起来，用于后续新 token 的生成 —— 这一缓存即为 KV cache。需要注意的是，一个 token 的 KV cache 依赖于其之前的所有 token，这意味着同一 token 出现在序列中不同位置时，其 KV cache 是不同的。

对于一个请求提示词，LLM 服务的生成计算可分解为两个阶段：

1. **提示词阶段**：以完整的用户提示词 (*x*1,...,*x**n*) 为输入，计算第一个新 token 的概率 *P*(*x**n*+1∣*x*1,...,*x**n*)。在此过程中，同时生成键向量 *k*1,...,*k**n* 和值向量 *v*1,...,*v**n*。由于提示词 token 是已知的，该阶段的计算可通过矩阵 - 矩阵乘法实现并行化，因此能高效利用 GPU 的固有并行性。
2. **自回归生成阶段**：依次生成剩余的新 token。在第 *t* 次迭代中，模型以单个 token *x**n*+*t* 为输入，结合键向量 *k*1,...,*k**n*+*t* 和值向量 *v*1,...,*v**n*+*t*，计算下一个 token 的概率 *P*(*x**n*+*t*+1∣*x*1,...,*x**n*+*t*)。需要注意的是，位置 1 到 *n*+*t*−1 的键向量和值向量已在之前的迭代中缓存，本迭代仅需计算新 token 对应的键向量 *k**n*+*t* 和值向量 *v**n*+*t*。该阶段会在序列达到最大长度（由用户指定或 LLM 限制）或生成序列结束（<<eos>）token 时终止。由于存在数据依赖，不同迭代的计算无法并行化，且通常采用效率较低的矩阵 - 向量乘法。因此，该阶段严重未能充分利用 GPU 的计算能力，受内存限制，且是单个请求延迟的主要来源。

## 2.3 LLM 的批量处理技术

通过批量处理多个请求，可提高 LLM 服务的计算利用率。由于多个请求共享同一模型权重，权重迁移的开销会在批量中的所有请求间均摊，且当批量规模足够大时，计算开销会占据主导地位，权重迁移的影响可忽略不计。然而，LLM 服务的批量处理并非易事，主要面临两个挑战：

1. 请求到达时间不一致：简单的批量策略要么让先到达的请求等待后到达的请求，要么让新请求等待之前的批量完成，都会导致显著的排队延迟。
2. 请求输入输出长度差异大（图 11）：直接的批量技术会对请求的输入和输出进行填充以统一长度，造成 GPU 计算和内存的浪费。

为解决这些问题，研究人员提出了细粒度批量机制，例如单元批量 [16] 和迭代级调度 [60]。与传统的请求级批量方法不同，这些技术在迭代级操作：每次迭代结束后，从批量中移除已完成的请求，并加入新的请求。因此，新请求只需等待一次迭代即可开始处理，无需等待整个批量完成。此外，借助专用 GPU 内核，这些技术无需对输入和输出进行填充。通过减少排队延迟和填充带来的低效问题，细粒度批量机制显著提高了 LLM 服务的吞吐量。



# 3 LLM 服务中的内存挑战

尽管细粒度批量处理减少了计算资源的浪费，并使请求能够以更灵活的方式进行批量处理，但可批量处理的请求数量仍受限于 GPU 内存容量 —— 尤其是分配给 KV cache 的存储空间。换句话说，服务系统的吞吐量受内存限制。要突破这一内存瓶颈，需要解决内存管理中的以下三大挑战：

------

## 3.1 庞大的 KV 缓存

KV cache 的大小会随请求数量快速增长。以 130 亿参数的 OPT 模型 [62] 为例，单个 token 的 KV cache 需占用 800KB 空间，计算方式为：2（键向量和值向量）× 5120（隐藏状态大小）× 40（层数）× 2（每个 FP16 数据占用的字节数）。由于 OPT 模型可生成最长 2048 个 token 的序列，单个请求的 KV cache 所需内存最高可达 1.6GB。当前 GPU 的内存容量通常为几十 GB，即便所有可用内存均分配给 KV cache，也仅能容纳几十个请求。此外，如图 2 所示，低效的内存管理会进一步减少批量大小。加之当前技术趋势下，GPU 的计算速度增长远超内存容量增长 [17]（例如，从 NVIDIA A100 到 H100，浮点运算能力（FLOPS）提升超过 2 倍，但 GPU 最大内存仍维持在 80GB），因此我们认为内存将成为日益关键的性能瓶颈。

------

## 3.2 复杂的解码算法

LLM 服务为用户提供了多种解码算法选择，每种算法对内存管理的复杂度要求不同。例如，在程序推荐等典型场景中 [18]，用户可能要求从单个输入提示词生成多个随机样本 —— 此时提示词对应的 KV cache（在我们的实验中占总 KV cache 内存的 12%，见 §6.3）可通过共享最大限度减少内存占用；而自回归生成阶段的 KV cache 则因样本结果不同且依赖上下文和位置信息，无法进行共享。KV cache 的共享程度取决于所采用的解码算法：在束搜索 [49] 等更复杂的算法中，不同的请求束（beam）可共享更大比例的 KV cache（最高可节省 55% 内存，见 §6.3），且共享模式会随解码过程动态演变。

------

## 3.3 输入与输出长度未知的调度问题

LLM 服务的请求在输入和输出长度上存在显著差异。这要求内存管理系统能够适配多种提示词长度；此外，随着解码过程中请求输出长度的增长，其 KV cache 所需内存也会不断扩大，可能耗尽用于处理新请求或现有提示词持续生成的可用内存。因此，系统需要做出调度决策，例如将部分请求的 KV cache 从 GPU 内存中删除或换出。

------

## 3.4 现有系统的内存管理方式

由于当前大多数深度学习框架 [33, 39] 要求张量存储在连续内存空间中，此前的 LLM 服务系统 [31, 60] 也将单个请求的 KV cache 存储为跨不同位置的连续张量。鉴于 LLM 的输出长度无法预测，这些系统会根据请求的最大可能序列长度，为每个请求静态分配一块连续内存 —— 无论请求的实际输入长度或最终输出长度如何。

图 3 展示了两个请求的内存分配情况：请求 A 的最大可能序列长度为 2048，请求 B 的最大可能序列长度为 512。现有系统的这种块预分配方案存在三类主要内存浪费：用于未来 token 的预留空间、因过度配置最大可能序列长度导致的内部碎片，以及来自伙伴分配器等内存分配器的外部碎片。其中，外部碎片永远无法用于存储生成的 token（服务请求前即可预知）；内部碎片同样无法被利用，但需在请求采样完成后才能确认，二者均属于纯粹的内存浪费。尽管预留空间最终会被使用，但在请求的整个生命周期内占用该空间（尤其是预留空间较大时），会导致其他请求无法利用这部分闲置资源。我们在实验中对内存浪费比例的可视化结果（图 2）显示，现有系统的实际有效内存占比最低仅为 20.4%。

尽管内存压缩 [54] 被提出作为解决碎片问题的潜在方案，但由于 KV cache 数据量庞大，在对性能敏感的 LLM 服务系统中执行压缩并不现实。即便支持压缩，现有内存管理系统为每个请求预分配的独立块空间，仍会阻碍解码算法特有的内存共享机制发挥作用。



# 4 方法

为解决第 3 节提出的挑战，本文设计了一种新的注意力算法 PagedAttention，并基于该算法构建了 LLM 服务引擎 vLLM。vLLM 的系统架构如图 4 所示，它采用集中式调度器协调分布式 GPU 工作节点的执行，KV 缓存管理器在 PagedAttention 的支持下，以分页方式高效管理 KV 缓存。具体而言，KV 缓存管理器通过集中式调度器发送的指令，管理 GPU 工作节点上的物理 KV 缓存内存。

接下来，我们将在 4.1 节描述 PagedAttention 算法；4.2 节和 4.3 节分别介绍 KV 缓存管理器的设计及其对 PagedAttention 的支持；4.4 节展示该设计如何为多种解码方法提供高效内存管理；4.5 节说明其对可变长度输入输出序列的处理方式；最后在 4.6 节阐述 vLLM 在分布式场景下的系统设计。

## 4.1 PagedAttention

为应对第 3 节所述的内存挑战，我们提出 PagedAttention—— 一种受操作系统中经典分页思想 [25] 启发的注意力算法。与传统注意力算法不同，PagedAttention 允许键向量和值向量存储在非连续内存空间中。具体而言，PagedAttention 将每个序列的 KV 缓存划分为多个 KV 块，每个块包含固定数量 token 的注意力键向量和值向量 ¹，我们将该数量称为 KV 块大小（𝐵）。分别用键块和值块表示，公式 4 中的注意力计算可转化为以下块级计算：

在注意力计算过程中，PagedAttention 内核会分别识别并获取不同的 KV 块。图 5 展示了 PagedAttention 的工作示例：键向量和值向量分布在三个块中，且这三个块在物理内存中并非连续存储。内核每次将查询 token（“forth”）的查询向量\(q_{i}\)与一个块中的键向量\(K_{j}\)（例如块 0 中 “Four score and seven” 对应的键向量）相乘，计算注意力分数，随后将\(A_{i j}\)与该块中的值向量\(V_{j}\)相乘，得到最终的注意力输出\(o_{i}\)。

## 4.2 KV 缓存管理器

vLLM 内存管理器的核心思想与操作系统中的虚拟内存 [25] 类似：操作系统将内存划分为固定大小的页，将用户程序的逻辑页映射到物理页，连续的逻辑页可对应非连续的物理内存页，使程序能以连续内存的方式访问；同时，物理内存无需提前完全预留，操作系统可按需动态分配物理页。

vLLM 借鉴虚拟内存的思想管理 LLM 服务中的 KV 缓存：在 PagedAttention 的支持下，将 KV 缓存组织为固定大小的 KV 块（类似虚拟内存中的页）。一个请求的 KV 缓存表现为一系列逻辑 KV 块，随着新 token 及其 KV 缓存的生成，这些逻辑块从左到右逐步填充，最后一个逻辑块中未填充的位置预留用于后续生成。

在 GPU 工作节点上，块引擎会分配一块连续的 GPU 显存，并将其划分为物理 KV 块（CPU 内存中也会执行此操作，用于换出；见 4.5 节）。KV 块管理器还维护块表，记录每个请求的逻辑 KV 块与物理 KV 块的映射关系，每个块表条目包含逻辑块对应的物理块编号及已填充位置数量。

分离逻辑 KV 块与物理 KV 块，使 vLLM 无需提前为所有位置预留内存即可动态扩展 KV 缓存，从而消除了现有系统中的大部分内存浪费（如图 2 所示）。

## 4.3 基于 PagedAttention 和 vLLM 的解码过程

下面结合图 6 的示例，说明 vLLM 如何执行 PagedAttention 并在单个输入序列的解码过程中管理内存：

1. 与操作系统虚拟内存类似，vLLM 无需在初始阶段为最大可能生成序列长度预留内存，仅预留足以容纳提示词计算阶段生成的 KV 缓存所需的 KV 块。例如，若提示词包含 7 个 token，vLLM 会将前 2 个逻辑 KV 块（0 和 1）映射到 2 个物理 KV 块（7 和 1）。在预填充步骤中，vLLM 采用传统自注意力算法（如 [13]）生成提示词的 KV 缓存和第一个输出 token，将前 4 个 token 的 KV 缓存存储在逻辑块 0 中，后 3 个 token 的 KV 缓存存储在逻辑块 1 中，剩余位置预留用于后续自回归生成阶段。
2. 在第一次自回归解码步骤中，vLLM 通过 PagedAttention 算法在物理块 7 和 1 上生成新 token。由于最后一个逻辑块仍有一个空闲位置，新生成的 KV 缓存会存储在此处，并更新块表中的 “已填充数量” 记录。
3. 在第二次解码步骤中，最后一个逻辑块已填满，vLLM 将新生成的 KV 缓存存储到新的逻辑块中：分配新的物理块（物理块 3），并在块表中记录该映射关系。

从全局来看，在每次解码迭代中，vLLM 首先选择一组候选序列进行批量处理（详见 4.5 节），为新需要的逻辑块分配物理块；随后将当前迭代的所有输入 token（即提示词阶段请求的全部 token 和生成阶段请求的最新 token）拼接为一个序列，输入 LLM；在 LLM 计算过程中，vLLM 通过 PagedAttention 内核访问以逻辑 KV 块形式存储的历史 KV 缓存，并将新生成的 KV 缓存保存到物理 KV 块中。

KV 块中存储多个 token（块大小 > 1），使 PagedAttention 内核能并行处理更多位置的 KV 缓存，提高硬件利用率并降低延迟；但块大小过大会增加内存碎片。4.2 节将探讨块大小的影响。

此外，随着更多 token 及其 KV 缓存的生成，vLLM 会动态为逻辑块分配新的物理块。由于所有块均从左到右填充，且仅当所有前序块填满时才分配新物理块，vLLM 将单个请求的内存浪费限制在一个块内，从而实现高效的内存利用（如图 2 所示），使更多请求能被批量放入内存，提升吞吐量。当一个请求完成生成后，其占用的 KV 块会被释放，用于存储其他请求的 KV 缓存。图 7 展示了 vLLM 同时管理两个序列内存的示例：两个序列的逻辑块映射到 GPU 工作节点块引擎预留空间内的不同物理块，相邻逻辑块无需在物理内存中连续，物理块空间可被两个序列高效利用。

## 4.4 对其他解码场景的支持

4.3 节介绍了 PagedAttention 和 vLLM 对基础解码算法（如贪心解码、采样）的支持，这类算法以单个用户提示词为输入，生成单个输出序列。在许多成功的 LLM 应用中 [18, 34]，LLM 服务需支持更复杂的解码场景，这些场景具有复杂的访问模式和更多内存共享机会。本节将展示 vLLM 在这些场景下的通用性。

### 4.4.1 并行采样

在基于 LLM 的程序助手 [6, 18] 中，LLM 会为单个输入提示词生成多个采样输出，用户可从候选结果中选择偏好的输出。此前我们默认一个请求生成单个序列，本节将扩展至更通用的场景 —— 一个请求生成多个序列。

在并行采样中，一个请求包含多个共享同一输入提示词的样本，因此提示词对应的 KV 缓存也可共享。借助 PagedAttention 和分页内存管理，vLLM 能轻松实现该共享，节省内存。

图 8 展示了双输出并行解码的示例：由于两个输出共享同一提示词，在提示词阶段仅预留一份提示词状态的存储空间，两个序列的提示词逻辑块映射到相同物理块 —— 两者的逻辑块 0 和 1 均映射到物理块 7 和 1。由于单个物理块可映射到多个逻辑块，vLLM 为每个物理块引入引用计数，此时物理块 7 和 1 的引用计数均为 2。

在生成阶段，两个输出采样不同的输出 token，需要独立的 KV 缓存存储。vLLM 为多个序列需要修改的物理块实现了块粒度的写时复制机制，类似操作系统虚拟内存中的写时复制技术（如创建进程的 fork 操作）。具体而言，如图 8 所示，当样本 A1 需要写入其最后一个逻辑块（逻辑块 1）时，vLLM 检测到对应的物理块（物理块 1）引用计数大于 1，便分配新物理块（物理块 3），指令块引擎复制物理块 1 的内容，并将物理块 1 的引用计数减至 1；随后样本 A2 写入物理块 1 时，其引用计数已为 1，因此可直接将新生成的 KV 缓存写入物理块 1。

综上，vLLM 允许多个输出样本共享提示词 KV 缓存的大部分空间，仅最后一个逻辑块通过写时复制机制管理。通过跨样本共享物理块，可大幅降低内存占用，尤其适用于长输入提示词场景。

### 4.4.2 束搜索

在机器翻译 [59] 等 LLM 任务中，用户期望 LLM 输出 top-k 个最合适的翻译结果。束搜索 [49] 是解码 LLM 最可能输出序列的常用算法，它通过束宽参数 k 控制每一步保留的最优候选序列数量。解码过程中，束搜索扩展束中每个候选序列，考虑所有可能的 token，利用 LLM 计算其概率，从候选序列中保留 top-k 个最可能的序列（其中 | V | 为词汇表大小）。

与并行解码不同，束搜索不仅支持初始提示词块的共享，还允许不同候选序列共享其他块，且共享模式随解码过程动态变化，类似操作系统中通过多次 fork 创建的进程树。图 9 展示了束宽 k=4 时，vLLM 对束搜索的 KV 块管理：在虚线所示迭代之前，每个候选序列已使用 4 个完整逻辑块，所有束候选共享第一个块（即提示词块）；候选 3 从第二个块开始与其他候选分岔；候选 0-2 共享前 3 个块，在第四个块分岔。

后续迭代中，top-4 个最可能的候选均源自候选 1 和 2，原始候选 0 和 3 不再属于最优候选，其逻辑块被释放，对应物理块的引用计数减少；vLLM 释放所有引用计数为 0 的物理块（块 2、4、5、8），分配新物理块（块 9-12）存储新候选的 KV 缓存。此时所有候选共享块 0、1、3；候选 0 和 1 共享块 6；候选 2 和 3 进一步共享块 7。

现有 LLM 服务系统需要在束候选之间频繁复制 KV 缓存，例如图 9 中虚线之后，候选 3 需复制候选 2 的大量 KV 缓存才能继续生成。vLLM 的物理块共享机制显著降低了这种频繁复制的开销：不同束候选的大部分块可直接共享，仅当新生成的 token 位于旧共享块内时，才像并行解码那样应用写时复制机制，且仅需复制单个块的数据。

### 4.4.3 共享前缀

LLM 用户通常会提供包含指令和示例输入输出的（长）任务描述（即系统提示词 [36]），该描述与实际任务输入拼接形成请求的提示词，LLM 基于完整提示词生成输出（如图 10 所示）。此外，通过提示词工程优化共享前缀，可提高下游任务的准确性 [26, 27]。

对于这类应用，多个用户提示词共享前缀，因此 LLM 服务提供商可提前存储前缀的 KV 缓存，减少前缀相关的冗余计算。在 vLLM 中，这一功能可通过以下方式便捷实现：服务提供商为预定义的共享前缀预留一组物理块（类似操作系统跨进程共享库的管理方式）；包含该共享前缀的用户输入提示词，可直接将其逻辑块映射到缓存的物理块（最后一个块标记为写时复制）；提示词阶段的计算仅需在用户的任务输入上执行。

### 4.4.4 混合解码方法

上述解码方法具有不同的内存共享和访问模式，但 vLLM 能同时处理具有不同解码偏好的请求，这是现有系统无法高效实现的。原因在于，vLLM 通过统一的映射层（将逻辑块转换为物理块）隐藏了不同序列间复杂的内存共享关系，LLM 及其执行内核仅需关注每个序列的物理块 ID 列表，无需处理序列间的共享模式。与现有系统相比，这种设计扩大了不同采样需求请求的批量处理机会，最终提升系统整体吞吐量。

## 4.5 调度与抢占机制

当请求流量超过系统容量时，vLLM 需优先处理部分请求。vLLM 采用先到先服务（FCFS）调度策略处理所有请求，确保公平性并避免饥饿；当需要抢占请求时，优先服务最早到达的请求，抢占最晚到达的请求。

LLM 服务面临一个独特挑战：输入提示词长度差异显著，输出长度无法提前预知（取决于输入提示词和模型）。随着请求数量和输出长度的增长，vLLM 可能耗尽 GPU 物理块，无法存储新生成的 KV 缓存。对此，vLLM 需要解决两个核心问题：（1）应换出哪些块？（2）若需重新使用换出的块，如何恢复？

通常，换出策略通过启发式算法预测最久未访问的块并换出。本文中，由于一个序列的所有块会被同时访问，因此采用 “全量换出或不换出” 策略 —— 要么换出一个序列的所有块，要么不换出。此外，一个请求中的多个序列（如束搜索请求中的束候选）会被成组调度为一个序列组，由于这些序列可能存在内存共享，因此始终被同时抢占或重新调度。

针对块恢复问题，vLLM 提供两种技术方案：

1. **换出（Swapping）**：这是大多数虚拟内存实现采用的经典技术，将换出的页复制到磁盘交换空间。本文中，vLLM 将换出的块复制到 CPU 内存：如图 4 所示，除 GPU 块分配器外，vLLM 还包含 CPU 块分配器，管理换出到 CPU 内存的物理块。当 vLLM 耗尽新 token 所需的空闲物理块时，选择一组序列换出，将其 KV 缓存转移到 CPU；抢占序列并换出其块后，vLLM 停止接收新请求，直至所有被抢占的序列完成处理；当一个请求完成后，其占用的块被释放，再将被抢占序列的块召回 GPU，继续处理该序列。需注意的是，该设计确保换出到 CPU 内存的块数量不超过 GPU 内存中的总物理块数量，因此 CPU 内存中的交换空间受限于分配给 KV 缓存的 GPU 内存大小。
2. **重计算（Recomputation）**：当被抢占的序列重新调度时，直接重计算 KV 缓存。由于解码阶段生成的 token 可与原始用户提示词拼接形成新提示词，所有位置的 KV 缓存可在一次提示词阶段迭代中生成，因此重计算的延迟可能显著低于原始延迟。

换出与重计算的性能取决于 CPU 内存与 GPU 内存之间的带宽以及 GPU 的计算能力，7.3 节将详细对比两者的速度。

------

## 4.6 分布式执行

许多 LLM 的参数规模超过单 GPU 内存容量 [5, 9]，因此需要将其分区部署在分布式 GPU 上，以模型并行的方式执行 [28, 63]，这要求内存管理器支持分布式内存。vLLM 通过支持 Transformer 上广泛使用的 Megatron-LM 风格张量模型并行策略 [47]，实现了高效的分布式执行。

该策略遵循 SPMD（单程序多数据）执行模式：线性层被划分为块级矩阵乘法，GPU 通过全归约（allreduce）操作持续同步中间结果；具体而言，注意力算子按注意力头维度拆分，每个 SPMD 进程负责多头注意力中的一个子集。

我们发现，即使采用模型并行执行，每个模型分片仍需处理相同的输入 token，因此需要相同位置的 KV 缓存。因此，vLLM 在集中式调度器中集成单个 KV 缓存管理器（如图 4 所示），不同 GPU 工作节点共享该管理器及逻辑块与物理块的映射关系。这种统一映射使 GPU 工作节点能根据调度器提供的物理块信息执行模型，尽管每个 GPU 工作节点拥有相同的物理块 ID，但仅存储其对应注意力头的部分 KV 缓存。

在每个步骤中，调度器首先为批量中的每个请求准备输入 token ID 和块表，将该控制消息广播给所有 GPU 工作节点；GPU 工作节点基于输入 token ID 执行模型，在注意力层中根据控制消息中的块表读取 KV 缓存；执行过程中，GPU 工作节点通过全归约通信原语同步中间结果，无需调度器协调（与 [47] 一致）；最后，GPU 工作节点将本次迭代的采样 token 返回给调度器。综上，GPU 工作节点无需在内存管理上同步，仅需在每次解码迭代开始时，与步骤输入一起接收所有内存管理信息。



# 5 实现

vLLM 是一款端到端的服务系统，包含 FastAPI [15] 前端和基于 GPU 的推理引擎。前端扩展了 OpenAI API [34] 接口，允许用户为每个请求自定义采样参数，例如最大序列长度和束宽 𝑘。

vLLM 引擎由 8500 行 Python 代码和 2000 行 C++/CUDA 代码编写而成。我们采用 Python 开发了调度器、块管理器等控制相关组件，同时为 PagedAttention 等关键操作研发了自定义 CUDA 内核。对于模型执行器，我们基于 PyTorch [39] 和 Transformers [58] 框架，实现了 GPT [5]、OPT [62]、LLaMA [52] 等主流 LLM。分布式 GPU 工作节点之间的张量通信通过 NCCL [32] 实现。

------

## 5.1 内核级优化

由于 PagedAttention 引入了现有系统未能高效支持的内存访问模式，我们针对性开发了多个 GPU 内核以优化性能：

1. **融合重塑与块写入**：在每个 Transformer 层中，新生成的 KV cache 会被分割为块，重塑为适配块读取的内存布局后，存储到块表指定的位置。为最大限度降低内核启动开销，我们将这些操作融合为单个内核。
2. **融合块读取与注意力计算**：适配 FasterTransformer [31] 中的注意力内核，使其能够根据块表读取 KV cache 并实时执行注意力计算。为确保合并内存访问（coalesced memory access），我们为每个块分配一个 GPU 线程束（warp）负责读取，并新增了对请求批次内可变序列长度的支持。
3. **融合块复制**：写时复制机制触发的块复制操作可能涉及非连续块，若使用 cudaMemcpyAsync API，会导致大量小数据传输调用。为缓解这一开销，我们实现了一个内核，将不同块的复制操作批量整合为单次内核启动。

------

## 5.2 支持多种解码算法

vLLM 通过三类核心方法实现了多种解码算法：分叉（fork）、追加（append）和释放（free）。分叉方法从现有序列创建新序列，追加方法向序列中添加新 token，释放方法用于删除序列。

例如，在并行采样场景中，vLLM 通过分叉方法从单个输入序列生成多个输出序列；随后在每次迭代中，通过追加方法向这些序列添加新 token，并通过释放方法删除满足停止条件（如生成 <<eos> token）的序列。该策略同样适用于束搜索和前缀共享场景。我们认为，通过组合这三类基础方法，未来可扩展支持更多新型解码算法。

## 6.1 实验设置

### 模型与服务器配置

我们选用了参数规模分别为 13B、66B 和 175B 的 OPT 模型 [62]，以及参数规模为 13B 的 LLaMA 模型 [52] 开展评估。13B 和 66B 是 LLM 排行榜 [38] 中广泛应用的模型规模，而 175B 则与知名的 GPT-3 模型 [5] 参数规模一致。所有实验均在 Google Cloud Platform 的 A2 实例（搭载 NVIDIA A100 GPU）上执行，详细的模型规模与服务器配置如表 1 所示。

### 工作负载

我们基于 ShareGPT [51] 和 Alpaca [50] 数据集合成实验工作负载，这两个数据集包含真实 LLM 服务的输入与输出文本。ShareGPT 数据集是用户与 ChatGPT [35] 的对话合集，Alpaca 数据集则是由 GPT-3.5 通过自指令（self-instruct）[57] 生成的指令数据集。我们对数据集进行分词处理，并利用其输入和输出长度分布合成客户端请求。如图 11 所示，ShareGPT 数据集的输入提示平均长度是 Alpaca 数据集的 8.4 倍，输出平均长度是其 5.8 倍，且长度方差更大。由于这些数据集未包含请求时间戳，我们采用泊松分布生成不同请求率下的请求到达时间。

### 基线系统

1. **FasterTransformer**：一款针对延迟进行高度优化的分布式推理引擎 [31]。由于 FasterTransformer 未自带调度器，我们参考现有服务系统（如 Triton [30]）的设计，实现了自定义动态批量调度器。具体而言，我们根据 GPU 内存容量，为每个实验设置尽可能大的最大批量大小 B，调度器会选取最多 B 个最早到达的请求组成批量任务，发送至 FasterTransformer 进行处理。

2. Orca

   ：当前最先进的面向吞吐量优化的 LLM 服务系统 [60]。由于 Orca 未公开提供可使用版本，我们自行实现了该系统。我们假设 Orca 采用伙伴分配算法确定 KV 缓存的内存地址，并基于请求输出的超额预留空间大小，实现了三个版本的 Orca：

   - Orca（Oracle）：假设系统已知每个请求的实际输出长度，该版本展示了 Orca 的理论性能上限，在实际场景中无法实现。
   - Orca（Pow2）：假设系统对输出空间的超额预留不超过 2 倍。例如，若实际输出长度为 25，则预留 32 个位置用于存储输出。
   - Orca（Max）：假设系统始终预留模型最大序列长度（即 2048 个 token）的空间。

### 关键指标

我们核心关注服务吞吐量。具体而言，我们基于不同请求率的工作负载，测量系统的归一化延迟 —— 即每个请求的端到端延迟均值除以其输出长度（与 Orca [60] 的指标定义保持一致）。高吞吐量的服务系统应在高请求率下仍维持较低的归一化延迟。大多数实验使用 1 小时的轨迹数据进行评估，例外的是 OPT-175B 模型，由于实验成本限制，使用 15 分钟的轨迹数据。

------

## 6.2 基本采样

我们在三个模型和两个数据集上，评估了 vLLM 在基本采样（每个请求对应一个样本）场景下的性能。图 12 第一行展示了 ShareGPT 数据集上的结果，曲线显示：随着请求率增加，延迟起初呈缓慢上升趋势，随后突然激增。这是因为当请求率超过服务系统的处理能力时，请求队列长度会无限增长，进而导致请求延迟急剧升高。

在 ShareGPT 数据集上，vLLM 在保持相近延迟水平的前提下，支持的请求率比 Orca（Oracle）高 1.7 倍–2.7 倍，比 Orca（Max）高 2.7 倍–8 倍。这一优势源于 vLLM 的 PagedAttention 能够高效管理内存，从而支持更多请求的批量处理。例如，如图 13a 所示，对于 OPT-13B 模型，vLLM 同时处理的请求数量是 Orca（Oracle）的 2.2 倍，是 Orca（Max）的 4.3 倍。与 FasterTransformer 相比，vLLM 支持的请求率最高可达其 22 倍，这是因为 FasterTransformer 未采用细粒度调度机制，且其内存管理方式与 Orca（Max）类似，存在显著低效问题。

图 12 第二行和图 13b 展示了 Alpaca 数据集上的结果，整体趋势与 ShareGPT 数据集一致。一个例外是图 12（f），该场景下 vLLM 相对于 Orca（Oracle）和 Orca（Pow2）的优势并不明显。这是因为 OPT-175B 的模型与服务器配置（表 1）提供了较大的 GPU 内存用于存储 KV 缓存，而 Alpaca 数据集的序列长度较短。在这种配置下，尽管 Orca（Oracle）和 Orca（Pow2）的内存管理存在低效问题，仍能批量处理大量请求，导致系统性能受计算能力限制而非内存限制。

------

## 6.3 并行采样与束搜索

我们通过两种常用采样方法（并行采样和束搜索），评估了 PagedAttention 中内存共享机制的有效性。在并行采样场景中，一个请求包含多个共享同一输入提示词的样本，因此提示词对应的 KV 缓存可通过共享减少内存占用。如图 14 第一行所示，随着采样序列数量的增加，vLLM 相对于 Orca 基线的性能提升更为显著。类似地，图 14 第二行展示了不同束宽下束搜索的结果：由于束搜索支持更多维度的内存共享，vLLM 的性能优势更加突出 —— 在 OPT-13B 模型和 Alpaca 数据集上，vLLM 相对于 Orca（Oracle）的性能提升从基本采样的 1.3 倍，提升至束宽为 6 时的 2.3 倍。

图 15 展示了内存节省比例（计算方式为：通过共享节省的块数量 ÷ 无共享时的总块数量）。在 Alpaca 轨迹的实验中，并行采样的内存节省比例为 6.1%–9.8%，束搜索的内存节省比例为 37.6%–55.2%。在 ShareGPT 数据集的相同实验中，并行采样的内存节省比例为 16.2%–30.5%，束搜索的内存节省比例为 44.3%–66.3%。

## 6.4 共享前缀

我们探究了 vLLM 在不同输入提示词共享前缀场景下的性能，如图 10 所示。实验采用多语言的 LLaMA-13B 模型 [52]，工作负载基于 WMT16 [4] 英德翻译数据集，并合成了两个包含指令和翻译示例的前缀：一个前缀包含 1 个示例（即单样本提示），另一个包含 5 个示例（即少样本提示）。如图 16（a）所示，当共享单样本前缀时，vLLM 的吞吐量是 Orca（Oracle）的 1.67 倍；当共享更多示例（图 16（b））时，vLLM 的吞吐量达到 Orca（Oracle）的 3.58 倍。

## 6.5 聊天机器人

聊天机器人 [8, 19, 35] 是 LLM 最重要的应用场景之一。为实现聊天机器人功能，我们将聊天历史与用户最新查询拼接为提示词，让模型生成响应。我们利用 ShareGPT 数据集合成聊天历史和用户查询，由于 OPT-13B 模型的上下文长度有限，我们将提示词截取至最后 1024 个 token，并限制模型最多生成 1024 个 token。我们不在不同对话轮次之间存储 KV 缓存，以免占用对话间隙其他请求的内存空间。

图 17 显示，vLLM 支持的请求率是三个 Orca 基线的 2 倍。由于 ShareGPT 数据集包含大量长对话，大多数请求的输入提示词长度为 1024 个 token。受伙伴分配算法限制，无论 Orca 基线如何预测输出长度，都会为请求输出预留 1024 个 token 的空间，因此三个 Orca 基线的性能表现相近。相比之下，vLLM 通过 PagedAttention 解决了内存碎片和预留问题，能够高效处理长提示词场景。



# 7 消融实验

本节通过消融实验，探究 vLLM 的各项关键设计，并评估这些设计选择的实际效果。

------

## 7.1 内核微基准测试

PagedAttention 中的动态块映射会影响涉及已存储 KV cache 的 GPU 操作性能，即块读写与注意力计算。与现有系统相比，本文提出的 GPU 内核（§5）需要额外承担块表访问、额外分支执行以及可变序列长度处理的开销。

如图 18（a）所示，相较于高度优化的 FasterTransformer 实现，这导致注意力内核延迟高出 20%–26%。我们认为该开销影响有限，因为它仅作用于注意力算子，而不影响模型中的其他算子（如线性算子）。尽管存在这一开销，PagedAttention 仍使 vLLM 在端到端性能上显著优于 FasterTransformer（§6）。

------

## 7.2 块大小的影响

块大小的选择对 vLLM 性能存在显著影响：块大小过小时，vLLM 可能无法充分利用 GPU 在 KV cache 读取和处理中的并行性；块大小过大时，内部碎片会增加，且内存共享的概率会降低。

如图 18（b）所示，我们在固定请求率下，基于 ShareGPT 和 Alpaca 轨迹，评估了不同块大小下 vLLM 的基本采样性能。在 ShareGPT 轨迹中，16 至 128 的块大小能实现最佳性能；在 Alpaca 轨迹中，16 和 32 的块大小表现良好，但更大的块大小会导致性能显著下降 —— 这是因为此时序列长度短于块大小，造成内存利用低效。

在实际应用中，我们发现块大小为 16 时，既能高效利用 GPU 资源，又能在大多数工作负载中避免显著的内部碎片。因此，vLLM 将默认块大小设置为 16。

------

## 7.3 重计算与换出机制的对比

vLLM 支持重计算和换出两种恢复机制。为明确两者的权衡关系，我们评估了它们的端到端性能，并对其开销进行微基准测试，结果如图 19 所示。

实验结果表明，块大小较小时，换出机制会产生巨大开销 —— 这是因为小块大小通常导致 CPU 与 GPU 之间存在大量小数据传输，进而限制了有效的 PCIe 带宽。相比之下，重计算的开销在不同块大小下保持稳定，因为重计算不依赖 KV 块的存储与传输。

因此，块大小较小时，重计算更高效；块大小较大时，换出机制更高效，但重计算的开销始终不超过换出机制延迟的 20%。对于 16 至 64 的中等块大小，两种方法的端到端性能相当。



# 8 讨论

## 虚拟内存与分页技术在其他 GPU 工作负载中的应用

虚拟内存与分页技术之所以能有效管理 LLM 服务中的 KV cache，是因为该工作负载需要动态内存分配（输出长度无法提前预知），且性能受 GPU 内存容量限制。但这一特性并非适用于所有 GPU 工作负载：例如，在深度神经网络（DNN）训练中，张量形状通常是静态的，因此内存分配可提前优化；再如，在非 LLM 的 DNN 服务中，内存效率的提升可能无法带来性能改善 —— 因为这类工作负载的性能主要受计算能力限制。在这些场景下，引入 vLLM 的相关技术可能因内存间接访问和非连续块内存带来的额外开销，反而导致性能下降。不过，我们期待 vLLM 的技术能被应用于其他与 LLM 服务具有相似特性的工作负载中。

## 应用虚拟内存与分页技术时的 LLM 特定优化

vLLM 通过充分利用应用特定语义，重新诠释并拓展了虚拟内存与分页技术的核心思想。例如，vLLM 采用 “全量换出或不换出” 的换出策略，这一设计源于 “处理一个请求需将其所有对应 token 状态存储在 GPU 内存中” 这一特性；再如，通过重计算恢复换出块的方法在操作系统中并不可行，但在 LLM 服务中具备实操性。此外，vLLM 通过将内存访问操作的 GPU 内核与注意力计算等其他操作的内核相融合，有效降低了分页技术中内存间接访问带来的开销。



# 9 相关工作

## 9.1 通用模型服务系统

模型服务是近年来的研究热点，已有众多系统针对深度学习模型部署的不同方面展开研究。Clipper [11]、TensorFlow Serving [33]、Nexus [45]、InferLine [10] 和 Clockwork [20] 等早期通用模型服务系统，围绕单模型或多模型服务的批量处理、缓存、部署与调度等问题进行了探索。

近年来，DVABatch [12] 提出了多入口多出口批量处理机制；REEF [21] 和 Shepherd [61] 提出了服务场景下的抢占式调度方案；AlpaServe [28] 利用模型并行实现统计复用。然而，这些通用系统未考虑 LLM 推理的自回归特性和 token 状态管理，导致未能充分挖掘优化潜力。

------

## 9.2 面向 Transformer 的专用服务系统

由于 Transformer 架构的重要性，研究人员开发了多款针对其的专用服务系统。这些系统通过 GPU 内核优化 [1, 29, 31, 56]、高级批量处理机制 [14, 60]、模型并行 [1, 41, 60] 及参数共享 [64] 等技术，提升服务效率。其中，Orca [60] 与本文提出的方案关联性最强。

### 与 Orca 的对比

Orca 的迭代级调度与 vLLM 的 PagedAttention 属于互补技术：两者均以提高 GPU 利用率、进而提升 LLM 服务吞吐量为目标，但 Orca 通过请求调度与交错执行，实现更多请求的并行处理；而 vLLM 通过提升内存利用率，让更多请求的工作集能适配 GPU 内存。

通过减少内存碎片并支持内存共享，vLLM 能在批量处理中容纳更多请求，相较于 Orca 实现 2-4 倍的性能提升。事实上，Orca 这类细粒度请求调度与交错执行会加剧内存管理的复杂性，这也使得本文提出的技术显得更为关键。

------

## 9.3 内存优化技术

加速器的计算能力与内存容量差距不断扩大，导致内存成为训练和推理的核心瓶颈。研究人员已采用换出 [23, 42, 55]、重计算 [7, 24] 及其组合 [40] 等技术降低训练过程中的峰值内存占用。

值得注意的是，FlexGen [46] 研究了在 GPU 内存有限的场景下，如何通过换出权重和 token 状态实现 LLM 推理，但并未针对在线服务场景设计；OLLA [48] 通过优化张量的生命周期和存储位置减少碎片，但不支持细粒度块级管理和在线服务；FlashAttention [13] 采用分块和内核优化，降低注意力计算的峰值内存并减少 I/O 开销。本文则在在线服务场景下，提出了块级内存管理的新思路。
